\section{Methodology}
\label{sec:methodology}

\subsection{System Architecture and Operational Flow}
\label{sec:architecture}

The proposed framework is implemented as a set of loosely coupled services that together generate and validate conflict-free 4D trajectories for structured U-Space corridor operations. The main logical components are:
(i) a \emph{Topology Registry} (Webserver) providing vertiports and the corridor network,
(ii) a \emph{Planner} responsible for route computation and iterative conflict checking,
and (iii) a \emph{U-space Service Provider (USSP)} responsible for flight-plan validation, authorization, and supervision. In the present implementation, NDMap-based conflict detection is executed within the Planner process rather than deployed as a separate service; it is depicted as a distinct logical block in Fig.~\ref{fig:architecture} for clarity of responsibilities.

\subsection{Global Route Planning on Corridor Graphs}
\label{sec:global_planning}

Global routing between vertiports is formulated as a shortest-path problem on a weighted graph \(G=(V,E)\),
where nodes \(V\) represent vertiports and edges \(E\) represent available corridor connections.
Edge weights correspond to geodesic distance between the connected endpoints (Haversine distance).
A* search is used to compute the shortest route between the selected origin and destination.
The heuristic is the straight-line geodesic distance to the destination, which is admissible and yields efficient convergence.
The output of this stage is an ordered list of corridor nodes:
\[
P = [v_0, v_1, \dots, v_n],
\]
which serves as the lateral (2D) reference route for subsequent trajectory generation.

\subsection{4D Trajectory Generation via CFMS}
\label{sec:trajectory_generation}

The route \(P\) is transformed into a flyable four-dimensional trajectory (latitude, longitude, altitude, time) using a waypoint synthesis step and a downstream trajectory generator. The implementation interfaces a Python-based Planner with the C++-based CFMS flight-management and 4D trajectory generation system~\cite{morscheck2021cfms}.

\paragraph{Inputs.}
The trajectory generation stage consumes:
(i) the node sequence \(P\),
(ii) vertiport coordinates and elevations,
(iii) a fixed cruise altitude layer, and
(iv) nominal phase-dependent speeds.
In this study, the cruise layer is defined as a fixed absolute altitude of \SI{200}{m} above mean sea level (MSL). This is a deliberate benchmark abstraction used to evaluate the computational behavior of the planning stack under controlled conditions. Accordingly, local terrain variation, obstacle constraints, and dynamic weather effects are not modeled in this stage of the evaluation, and the resulting trajectories should be interpreted as benchmark trajectories rather than operational flight plans.

\paragraph{Waypoint synthesis and phase annotation.}
A compact waypoint list \(W=[w_1,\dots,w_m]\) is synthesized from \(P\) by adding a small number of vertical-profile waypoints:
a departure waypoint at the origin pad elevation, an intermediate climb waypoint, cruise waypoints aligned with corridor nodes at the cruise altitude layer, a descent-initiation waypoint, and a final waypoint at the destination pad elevation.
Each waypoint is annotated with a nominal phase label (takeoff, cruise/transition, landing) and an associated target speed.
Nominal speeds are derived from vehicle performance limits scaled by a safety factor to preserve flyability margins.

\paragraph{CFMS execution and subsampling.}
The annotated waypoint list is converted into the CFMS input format (WGS-84 coordinates, altitudes, phase and speed fields) and passed to CFMS to produce a dense, time-parameterized trajectory \(\mathcal{T}\) satisfying the kinematic profile~\cite{morscheck2021cfms}.
To reduce payload size for downstream processing and visualization, \(\mathcal{T}\) is uniformly subsampled to a fixed maximum number of points while retaining the first and last samples.

\subsection{Conflict Detection in 4D Using NDMap}
\label{sec:conflict_detection}

Conflicts are detected using NDMap~\cite{NDMap}, configured over the 4D state space \((\lambda,\varphi,H,t)\) (longitude, latitude, altitude, time). NDMap indexes previously accepted trajectories and efficiently identifies segments of an inspected candidate trajectory that violate separation minima with respect to the active set.

\paragraph{Configuration and output.}
Separation requirements are parameterized by minimum spacing thresholds in each dimension (horizontal, vertical, and temporal).
For each detected conflict, NDMap returns one or more time intervals \([t_{\text{start}}, t_{\text{end}}]\) indicating when the candidate violates separation with any active trajectory. These intervals are used as the primary input to the resolution loop.

\subsection{Conflict Resolution by Lateral Re-routing}
\label{sec:conflict_resolution}

Conflict resolution is implemented directly within the planning loop using \emph{lateral re-routing} on the corridor graph. The procedure is iterative:
(1) compute a candidate route using A*,
(2) generate a 4D trajectory and perform conflict detection using NDMap,
(3) if conflicts are present, penalize corridor edges belonging to the conflicting candidate route by assigning them a very large cost (effectively removing them from consideration),
and (4) re-run A* on the modified graph.
The loop terminates when NDMap reports no conflicts or when no feasible alternative route exists.

NDMap, as a trajectory-conflict management concept, can support several resolution dimensions, including changes in time, direction, and altitude~\cite{NDMap}. In the present implementation, however, NDMap is used only for conflict detection. The actual resolution mechanism is restricted to lateral re-routing in the corridor graph; no departure-time adjustment, speed-based temporal shift, or altitude-layer change is applied.

This strategy is intentionally conservative and simple: it preserves the overall system modularity and enables scalable online admission control while illustrating how embedded 4D conflict checks can be integrated into a microservice-oriented planning pipeline. More expressive resolution strategies based on temporal or vertical deconfliction are left for future work.
