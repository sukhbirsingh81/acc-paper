\section{Materials and Methods}
\label{sec:methodology}

\subsection{System Architecture and Operational Flow}
\label{sec:architecture}

The proposed framework is implemented as a set of loosely coupled software services designed to generate and locally screen candidate 4D trajectories for structured corridor operations within U-space. The services are part of a larger microservice fleet-control architecture for UAM operations~\cite{nagel2026microservice}. The main logical components relevant to this paper are:
(i) a browser-based \emph{operator user interface} (UI), implemented as a web application (webapp) and used by the fleet operator to prepare and supervise operations,
(ii) a \emph{fleet webserver} acting as backend-for-frontend (BFF) for the operator UI; it is the only service the browser communicates with, owns the local plan state, provides the vertiport and corridor-network topology, and invokes the other service contracts server-side,
(iii) a \emph{Planning Service} responsible for route computation, waypoint synthesis, CFMS-based 4D trajectory generation, and request-local re-planning,
(iv) a \emph{Deconfliction Service} responsible for NDMap-based conflict detection and conflict reporting, and
(v) a \emph{USSP-facing operation-plan boundary} through which a locally prepared candidate trajectory could later be submitted for U-space authorization, traffic-information handling, and lifecycle recording.

Two existing DLR tools are embedded in these services. CFMS is a modular experimental flight-management and 4D trajectory generation system for unmanned multicopter, UAM, and other VTOL aircraft; given a phase-structured waypoint sequence with altitude, speed, and flight-phase information, it generates a dense, kinematically consistent, time-parameterized 4D trajectory~\cite{morscheck2021cfms}. NDMap is a high-performance conflict-detection and -resolution library for multi-dimensional objects; it indexes trajectories in a combined space--time state space and efficiently identifies separation violations between a candidate trajectory and a set of existing trajectories~\cite{NDMap}. In this framework, CFMS is used inside the Planning Service for trajectory generation, while NDMap is used inside the Deconfliction Service for conflict detection.

The architecture separates trajectory generation from conflict assessment. The Planning Service produces candidate 4D trajectories and owns graph modification for re-planning, while NDMap-based conflict assessment is encapsulated in the Deconfliction Service. This separation keeps routing and trajectory-generation logic independent from NDMap conflict-state management and enables each responsibility to be deployed or scaled separately.

The USSP-facing boundary follows the authority split used in U-space fleet-control architectures~\cite{nagel2026microservice}: the operator-side planning system prepares route intent, candidate trajectories, and local feasibility evidence, while the USSP remains the authority for U-space decisions such as operation-plan authorization, traffic information, geo-awareness, and lifecycle records. In the deployed workflow, the fleet webserver submits a versioned operation plan (U-plan) to the USSP, and the USSP applies its authorization workflow, consulting the Deconfliction Service where applicable, before accepting, requesting changes to, or rejecting the plan; the Planning and Deconfliction Services are providers inside this flow and do not authorize operations themselves~\cite{nagel2026microservice}. Changes to the trajectory, time window, constraints, reservations, or aircraft profile would require a new submitted plan version. The experiments in this paper stop before this authorization step. Therefore, the reported retained trajectories should be interpreted as locally deconflicted candidate plans, not as USSP-authorized operations.

\subsection{Global Route Planning on Corridor Graphs}
\label{sec:global_planning}

Global routing between vertiports is formulated as a shortest-path problem on a weighted graph \(G=(V,E)\), where nodes \(V\) represent vertiports and edges \(E\) represent available corridor connections. Edge weights are defined by the geodesic distance between connected endpoints, computed using the Haversine formula. A* search is used to compute the shortest route between the selected origin and destination.

The heuristic is the straight-line geodesic distance from the current node to the destination. This heuristic is admissible because any route constrained to graph edges cannot be shorter than the direct geodesic distance to the destination. The output of this stage is an ordered list of corridor nodes,
\[
P = [v_0, v_1, \dots, v_n],
\]
which serves as the lateral reference route for subsequent waypoint synthesis and trajectory generation.

\subsection{4D Trajectory Generation via CFMS}
\label{sec:trajectory_generation}

The route \(P\) is transformed into a phase-consistent four-dimensional trajectory (latitude, longitude, altitude, time) using a waypoint synthesis step and the CFMS flight-management and 4D trajectory generation system~\cite{morscheck2021cfms}. Algorithm~\ref{alg:planner_pipeline} summarizes the resulting planner pipeline; the individual steps are detailed in the remainder of this section.

\begin{Algorithm}[Planner pipeline for 4D trajectory generation]
\label{alg:planner_pipeline}
\begin{algorithmic}[1]
\REQUIRE Origin vertiport \(o\), destination vertiport \(d\), corridor graph \(G=(V,E)\), vertiport data, cruise altitude \(H_c\)
\ENSURE Dense trajectory \(\mathcal{T}_{\mathrm{dense}}\)
\STATE Compute corridor route \(P\) from \(o\) to \(d\) using A* on \(G\)
\STATE Generate phase-structured waypoint sequence \(W\) from \(P\), vertiport data, and \(H_c\)
\STATE Convert \(W\) into CFMS-compatible input
\STATE Generate dense 4D trajectory \(\mathcal{T}_{\mathrm{dense}}\) using CFMS
\RETURN \(\mathcal{T}_{\mathrm{dense}}\)
\end{algorithmic}
\end{Algorithm}

A* provides the lateral corridor-node sequence, while the waypoint synthesizer inserts terminal waypoints around the departure and arrival vertiports. The resulting phase-structured waypoint sequence is then converted into CFMS input for dense 4D trajectory generation. \paragraph{Inputs.}
The trajectory generation stage consumes:
(i) the node sequence \(P\),
(ii) vertiport coordinates and elevations,
(iii) a fixed cruise altitude layer, and
(iv) nominal phase-dependent speeds.
In this study, the cruise layer is defined as a fixed absolute altitude of \SI{200}{m} above MSL. Because the altitude is defined in MSL, the height above ground may vary with terrain and pad elevation. This is a deliberate benchmark abstraction used to evaluate the computational behavior of the planning stack under controlled conditions. Accordingly, local terrain variation, obstacle constraints, and dynamic weather effects are not modeled in this stage of the evaluation, and the resulting trajectories should be interpreted as benchmark trajectories rather than operational flight plans.

\paragraph{Nominal waypoint synthesis.}
At a high level, the waypoint generator converts the lateral A* route into a small set of phase-labeled waypoints representing departure, climb, cruise, descent, and landing. The lateral corridor path \(P\) is converted into a compact waypoint sequence \(W=[w_1,\dots,w_m]\) that explicitly represents the take-off, climb, cruise, descent, and landing phases. The first and last waypoints coincide with the origin and destination pad locations, respectively. Between these endpoints, the waypoint synthesizer inserts a small number of additional waypoints to shape the vertical profile and to provide CFMS with a phase-structured route definition.

For multi-node routes, intermediate corridor nodes are retained as cruise-route reference points. Their lateral coordinates follow the graph path, while their altitudes are assigned according to the nominal climb profile up to the fixed cruise layer. For direct origin--destination connections, a reduced waypoint set is generated, including an intermediate point on the connecting geodesic to support smooth transition between departure and arrival phases.

At internal cruise-route nodes, the waypoint generator retains the A*-selected graph nodes as centerline references for the CFMS-compatible waypoint list. The evaluated trajectory-generation step does not explicitly impose a corridor-width-derived turn or swept-volume constraint. Any local smoothing, turning behavior, or speed adjustment around adjacent route legs should therefore be interpreted as part of the trajectory-generation behavior for the synthesized waypoint sequence, not as evidence of a validated corridor-width turn model. Explicit swept-volume containment against a lateral corridor envelope remains outside the scope of the present benchmark.

Each waypoint is annotated with a nominal flight phase and an associated target speed. The phase labels distinguish terminal segments near the vertiports from the cruise and transition segments along the corridor network. Nominal speeds are derived from aircraft-performance limits and scaled to preserve operational margins.

\paragraph{Terminal procedure construction.}
The departure and arrival portions of \(W\) are generated using a simplified vertiport terminal-procedure model. At departure, the synthesized waypoint sequence begins at the pad elevation, continues with a vertical climb segment, and then transitions into the outbound corridor direction. At arrival, the sequence is constructed analogously in reverse, guiding the aircraft from the inbound corridor segment toward the destination pad through a constrained descent geometry.

To keep these terminal segments geometrically structured, the waypoint generator uses a parameterized obstacle-free volume, referred to here as a ``verticone,'' around each vertiport; \emph{verticone} is manuscript terminology for this construction and not an EASA-defined regulatory term. Intuitively, the verticone defines a protected three-dimensional terminal volume above and around the pad: close to the pad the motion is mostly vertical, whereas at greater height the allowable lateral footprint becomes wider. In this study, these geometry parameters are simplified constructions inspired by the European Union Aviation Safety Agency (EASA) Prototype Technical Specifications for the Design of Visual Flight Rules (VFR) Vertiports (PTS-VPT-DSN), in particular the vertical take-off and landing procedure and OFV definitions in Chapter~D, Subpart~2~\cite{easa2022_pts_vpt_dsn}. The synthesized terminal waypoints are intended to remain within this simplified admissible-volume construction; exact conformance with the EASA specifications has not been verified, and this does not constitute a certification or operational procedure assessment.

Here, \(h_1\) denotes the lower terminal reference height, \(h_2\) the upper terminal reference height, LDP the landing decision point, OFV the obstacle-free volume, and OLS the outer limitation surface. For departure, the aircraft first climbs vertically from the pad to a lower terminal height \(h_1\). It then transitions toward a second reference height \(h_2\) while aligning with the outbound corridor direction. If enough horizontal distance is available, the climb can be extended farther along the same centerline toward the outer limitation surface at up to \SI{152}{m} above the pad, limited by the cruise altitude. For arrival, the logic is reversed: the trajectory may first pass through a top-of-descent point on the inbound centerline, then enters the OFV at \(h_2\), transitions to an over-pad waypoint at \(h_1\), passes the LDP reference height, and finishes at the pad.

This procedure produces a sparse, geometrically structured nominal waypoint set that preserves the corridor-based lateral route while explicitly modeling the terminal altitude transitions required before and after cruise flight. Contingency and non-nominal terminal procedures are outside the scope of the present evaluation.

\paragraph{CFMS execution.}
The annotated waypoint list is converted into the CFMS input format using World Geodetic System 1984 (WGS-84) coordinates, altitudes, flight-phase labels, and speed fields. CFMS then produces a dense, time-parameterized trajectory \(\mathcal{T}_{\mathrm{dense}}\) satisfying the prescribed kinematic profile~\cite{morscheck2021cfms}. The trajectory-generation runtimes reported in the evaluation are measured for CFMS invocation and dense trajectory generation.

\subsection{Deconfliction Service Using NDMap}
\label{sec:conflict_detection}

Conflict detection is assigned to the separate Deconfliction Service. The service uses NDMap~\cite{NDMap}, configured over the 4D state space \((\lambda,\varphi,H,t)\), corresponding to longitude, latitude, altitude, and time, to index the referenced trajectories and identify the instants at which an inspected candidate trajectory violates the separation minima with respect to the peer set. This keeps conflict-management state and NDMap-specific data structures outside the Planning Service.

\paragraph{Conflict predicate.}
Trajectories enter the detector as discrete 4D samples
\[
s^{X}_{k} = \bigl(\mathbf{r}^{X}_{k},\, t^{X}_{k}\bigr),
\qquad
\mathbf{r}^{X}_{k} = \bigl(\lambda^{X}_{k}, \varphi^{X}_{k}, H^{X}_{k}\bigr),
\]
of trajectory \(X\), where \(\mathbf{r}^{X}_{k}\) is the position at sample time \(t^{X}_{k}\), with longitude \(\lambda\) and latitude \(\varphi\) in WGS-84 degrees (converted to radians at the detector input), altitude \(H\) in meters MSL, and \(t\) in epoch seconds; the CFMS sampling interval is approximately \SI{1}{s}. The detector does not compare a sample of one trajectory against a sample of the other. It evaluates both trajectories at one common instant \(t\), obtaining each position by linear interpolation between the two samples of that trajectory which bracket \(t\),
\begin{equation}
\label{eq:traj_interpolation}
\mathbf{r}^{X}(t) = (1-\alpha)\,\mathbf{r}^{X}_{k} + \alpha\,\mathbf{r}^{X}_{k+1},
\qquad
\alpha = \frac{t - t^{X}_{k}}{t^{X}_{k+1} - t^{X}_{k}},
\qquad
t \in \bigl[t^{X}_{k},\, t^{X}_{k+1}\bigr],
\end{equation}
which yields the interpolated components \(\mathbf{r}^{X}(t) = (\lambda^{X}(t), \varphi^{X}(t), H^{X}(t))\). Two trajectories \(A\) and \(B\) are in instantaneous conflict at time \(t\) if and only if
\begin{equation}
\label{eq:conflict_predicate}
\begin{aligned}
\mathcal{C}_{AB}(t) \iff\;
  & t \in \mathcal{T}_{AB} \\
  &\wedge\; d_{\mathrm{geo}}\bigl((\lambda^{A}(t), \varphi^{A}(t)),\,
      (\lambda^{B}(t), \varphi^{B}(t))\bigr) < d_{\mathrm{lat}} \\
  &\wedge\; \bigl\lvert H^{A}(t) - H^{B}(t) \bigr\rvert \le d_{\mathrm{vert}},
\end{aligned}
\end{equation}
with \(\mathcal{T}_{AB} = [t^{A}_{0}, t^{A}_{\mathrm{end}}] \cap [t^{B}_{0}, t^{B}_{\mathrm{end}}]\) the intersection of the two trajectory time intervals. The horizontal and vertical criteria are evaluated on different components of \(\mathbf{r}^{X}(t)\): only longitude and latitude enter the horizontal distance \(d_{\mathrm{geo}}\), while altitude is compared separately. Here \(d_{\mathrm{geo}}\) is the geodesic distance on the WGS-84 ellipsoid, computed with Vincenty's inverse formula; \(d_{\mathrm{lat}} = 0.3\,\mathrm{NM} \approx \SI{555.6}{m}\) with NM denoting nautical miles; and \(d_{\mathrm{vert}} = 100\,\mathrm{ft} = \SI{30.48}{m}\). The horizontal comparison is strict and the vertical comparison is non-strict, exactly as written in Equation~(\ref{eq:conflict_predicate}); unit tests bracket each threshold from both sides and pin the boundary case. The vertical threshold is configured in feet and converted to meters at the configuration boundary, so the comparison operates entirely in the trajectory altitude unit. Horizontal separation is thus a single geodesic distance, not separate latitude/longitude thresholds. The graph-search distances of Section~\ref{sec:global_planning} use a different and simpler computation---the spherical Haversine formula---and are unrelated to Equation~(\ref{eq:conflict_predicate}).

No pairwise sample-time tolerance is used. Each trajectory is independently interpolated to the same evaluation instant before the separation predicate is applied, so the time difference between the two evaluated positions in Equation~(\ref{eq:conflict_predicate}) is zero by construction and the predicate contains no temporal tolerance term.

\paragraph{From the predicate to a reported conflict.}
Two steps precede and follow Equation~(\ref{eq:conflict_predicate}) and are easily conflated with it. Beforehand, a pair of trajectories is considered only over \(\mathcal{T}_{AB}\): if their time intervals are disjoint the pair is discarded without any spatial evaluation. Overlapping intervals are therefore a precondition for examining a pair, not a conflict in themselves, and two trajectories that share their entire time interval are conflict-free whenever no common instant satisfies Equation~(\ref{eq:conflict_predicate}). Afterwards, the instants that satisfy the predicate are aggregated into conflict intervals \([t_{\text{start}}, t_{\text{end}}]\), with violations separated by the configured merge gap of \SI{2}{s} or less combined into one interval. For each reported interval the Deconfliction Service then determines the closest approach, defined as the instant of minimum co-temporal horizontal separation within the interval, and reports that instant together with the horizontal distance and vertical separation there. The interval and its closest-approach time are the input to the Planning Service's request-local lateral re-routing loop of Section~\ref{sec:conflict_resolution}.

\paragraph{Sampling and completeness.}
At the evaluated cruise speed of approximately \SI{25}{m/s}, consecutive trajectory samples are about \SI{25}{m} apart, which is small against the \SI{555.6}{m} horizontal threshold, and the linear interpolation of Equation~(\ref{eq:traj_interpolation}) approximates the straight, constant-speed cruise segments of the generated trajectories closely. The evaluated implementation nevertheless does not provide a formal continuous-time completeness guarantee, because the predicate is evaluated at sampled instants and violation intervals shorter than \SI{1}{s} are not reported.

The consequence can be bounded for one idealized case. Consider two aircraft on straight-line relative motion with constant horizontal relative speed \(v_{\mathrm{rel}}\) and minimum horizontal separation \(d_{\min} < d_{\mathrm{lat}}\), and assume the vertical criterion of Equation~(\ref{eq:conflict_predicate}) is satisfied throughout the encounter. The horizontal criterion then holds for a duration of \(2\sqrt{d_{\mathrm{lat}}^{2} - d_{\min}^{2}}/v_{\mathrm{rel}}\), which tends to zero as \(d_{\min}\) approaches \(d_{\mathrm{lat}}\). At \(v_{\mathrm{rel}} = \SI{50}{m/s}\), an encounter with \(d_{\min} \gtrsim \SI{555.0}{m}\) therefore stays below the \SI{1}{s} floor and goes unreported. These assumptions do not hold in general---real encounters include turns, speed changes and vertical motion---so the expression is an order-of-magnitude bound for grazing geometries rather than a general miss criterion. Such marginal encounters are, by construction, the ones closest to the threshold rather than deep violations, but the detector should be read as reporting sampled separation violations of at least \SI{1}{s} duration, not as a continuous-time separation proof. This behavior is covered by the accompanying unit tests, which bracket both thresholds and include a grazing encounter below the duration floor.

\paragraph{Detector state lifecycle.}
In the evaluated deployment, detector state is rebuilt for each conflict check rather than maintained incrementally across requests. Every check fetches the candidate and all referenced peer trajectories from the Planning Service's trajectory store over the Hypertext Transfer Protocol (HTTP), builds the detector state from them, and discards it once the check returns; the Deconfliction Service is therefore stateless across requests. The candidate keeps the same trajectory identifier across re-planning attempts, and each attempt overwrites the persisted trajectory before the next check, so an obsolete candidate cannot leak into later checks; duplicate insertion and self-conflict are excluded by identifier deduplication and by reporting only conflicts that involve the candidate. This design trades per-check cost, which grows with the peer-set size, for state consistency: because no detector state survives a request, multi-worker deployments cannot diverge, but a shared trajectory store would be required beyond a single host. The latency consequences are quantified in Section~\ref{sec:conflict_resolution_results}.

\subsection{Conflict Resolution by Lateral Re-routing}
\label{sec:conflict_resolution}

Conflict resolution is implemented using \emph{lateral re-routing} on the corridor graph. Route segments associated with a detected conflict are discouraged for the current request, and A* is re-run to search for an alternative corridor sequence. The procedure is iterative:
(1) the Planning Service generates a candidate route using A*,
(2) the corresponding 4D trajectory is generated and checked by the Deconfliction Service using NDMap,
(3) if conflicts are detected, the reported conflict times are mapped back to coordinates on the candidate trajectory,
(4) the nearest edge of the selected A* route is identified for each mapped conflict coordinate,
(5) the affected directed edges are removed from the request-local graph by assigning them effectively infinite weight,
\[
  d(u,v) := \infty, \qquad (u,v)\in E_{\text{conflict}},
\]
and
(6) A* is re-executed on the modified graph.
The loop terminates when NDMap reports no conflicts, when no new conflicting edge can be identified, when no feasible alternative route remains, or when the configured retry limit is reached. Figure~\ref{fig:conflict_resolution_re-routing} illustrates steps (4)--(6) on a small example graph.

\paragraph{Conflict-to-edge mapping.}
Steps (3)--(5) are defined precisely as follows. For each conflict record, the mapping time \(t^{*}\) is the reported closest-approach time of Section~\ref{sec:conflict_detection} if present, otherwise the midpoint \((t_{\text{start}} + t_{\text{end}})/2\), otherwise \(t_{\text{start}}\); a record without any time field is skipped and counted as a mapping failure. For trajectory-pair conflicts the closest-approach time is always present, so \(t^{*}\) is the instant of minimum co-temporal horizontal separation within the reported interval, and the mapped sample is the point of the candidate trajectory at which the encounter is closest. The candidate sample nearest to \(t^{*}\) in absolute time difference is selected. Its position is then compared against every directed edge \((u,v)\) of the currently selected route using the point-to-segment distance in a local equirectangular projection around the sample latitude, and the edge with the smallest distance is chosen; when a sample lies exactly on a shared route node, and two adjacent edges are equidistant, the strict-minimum comparison keeps the earlier edge in path order. Only the flown direction \((u,v)\) is removed; the opposite direction \((v,u)\) remains available to other routes and later attempts. Several conflicts mapping to the same edge block it once. No maximum accepted mapping distance is enforced; because the mapped sample lies on the candidate trajectory and the route is the trajectory's lateral reference, mapping distances are bounded in practice by the terminal-procedure geometry, but a formal bound is not imposed and this is a known limitation. If an iteration produces no edge that is not already blocked, the loop reports a distinct \emph{mapping-stall} outcome (\texttt{stalled\_no\_new\_edges}), which the evaluation reports separately from retry-limit and no-route outcomes. The unit tests accompanying the implementation cover the tie-breaking, duplicate-conflict, direction, and mapping-failure cases.

NDMap can support conflict-management strategies across several resolution dimensions, including changes in time, direction, and altitude~\cite{NDMap}. In the present framework, NDMap is used for conflict detection, while the Planning Service modifies a request-local copy of the corridor graph and requests lateral re-routing. The current resolution mechanism is restricted to lateral re-routing in the corridor graph; no departure-time adjustment, speed-based temporal shift, or altitude-layer change is applied.

This strategy is intentionally conservative and simple. It avoids changing the persistent topology: edge removals are request-local and are used only while recomputing the candidate trajectory under evaluation. The trade-off is that resolved routes may be longer, and some conflicts may not be solvable by lateral re-routing alone if all useful alternatives are removed or if the graph becomes disconnected. More expressive resolution strategies based on temporal or vertical deconfliction are left for future work.
